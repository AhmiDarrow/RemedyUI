# RemedyUI roadmap

Each milestone ends with something real running and tested. From M5 on, each also ends with a Remedy app moved onto the engine. Apps go smallest first, so each one proves a new part of the engine before the large ones depend on it. Every pack an app needs lands in that app's milestone or earlier. This file is the source of truth for milestone numbers; [APPS.md](APPS.md) refers to it.

Nothing is merged as a placeholder: a crate enters the workspace with its first real code and tests. Each milestone is judged by repeat runs of its scenario suites, its benchmarks against their targets, and its fuzzers.

## M3. Layout, style, input and semantics

**Status:** built, with the open items listed at the end. `remedy-ui-layout` is built: flex, grid and block through taffy behind RemedyUI's own styles; a viewport root, so an auto-width root fills the window like a page body; inherited direction with logical insets mirrored for right to left; measured leaves; absolute and pixel-snapped rects; and the virtual list (estimates, Fenwick offsets, anchoring through inserts, removals and re-measures, stick-to-end, jump to any row).
`remedy-ui-motion` is built: cubic-Bézier easing with the standard curves, tweens, closed-form springs (stiffness and damping, or duration and bounce), retargeting that keeps position and velocity, animatable geometry and Oklab colors, the frame clock with presentation-time prediction and deadlines, and reduced motion. `remedy-ui-style` is built: typed themes (color roles, type scale, spacing, radii, motion, density), Dark Forest from RemedyAI's palette, derived tokens with Oklab-preserving contrast balancing (text AAA, muted and on-accent AA), state flags, and variant- and state-aware resolution cached by theme version. `remedy-ui-input` is built: the event model (pointers with kind, buttons, pressure and coalesced history; layout-aware keys with physical position and composing state; wheels), least-squares velocity, the gesture arena (tap, long press, pan, axis pans, platform slops), scroll axes with exponential fling decay and clamped or rubber-band edges, and the command table with scopes, enabled state, rebinding with conflict checks and platform chord labels. `remedy-ui-a11y` is built. It provides:
- RemedyUI's semantics model (roles, labels, values, numeric ranges, states, actions, set positions, live regions, hidden)
- incremental AccessKit tree updates that start only when a client connects
- merged rows with composed labels
- password inputs whose text is never exposed, not even through a merged parent

Open in M3:
- AccessKit ships no schema validator. The tests check that the produced updates have the expected roles, names, values and structure.
- Wiring these crates into the tree and frame (bindings that set semantics, styles and layout from elements) arrives with the first widgets in M5, which is where they first have callers.

**Crates:** `layout` (taffy behind RemedyUI types, pixel snapping, virtualization with anchoring), `style` (tokens, derived tokens, states, contrast helpers), `input` (event model, hit testing, gesture arena, scroll physics, focus, commands), `a11y` (semantics tree and incremental AccessKit updates), and `motion` (frame clock, transitions, springs). All of it is tested headless.

**Done when:**
- layout snapshots match references
- a virtual list keeps its anchor through inserts above it
- the gesture arena resolves nested pans
- the semantics tree passes AccessKit's schema checks for test scenes

## M4. Rendering, the compositor and Windows

**Status:** built (PRs #18-#27). `remedy-ui-paint` is built: display lists of rounded rects, borders, shadows, paths and strokes, gradients, glyph runs, images, clips, layers and transforms, with conservative bounds. `remedy-ui-render-cpu` is built: it draws display lists through vello_cpu at any device scale, with glyphs rasterized by RemedyUI's own hinted rasterizer, cached per size and subpixel bin, and composited in order so clips and layers apply. `remedy-ui-compositor` is built: layer trees shared through `Arc` and handed over in a single-slot mailbox; compositor-owned scroll offsets with fling and overscroll physics and wheel routing that hands an exhausted inner scroller outward; compositor-side offset, scale and opacity animations (reduced motion honored); 256/512-pixel tiles, rastered visible-first with a one-tile prefetch ring inside scroll containers, released on memory pressure or scale change; and per-layer damage in device pixels. `CpuCompositor` runs the plans, and its frames match direct rendering. `remedy-ui-render-gpu` is built: a backend ladder (D3D12/Vulkan/Metal, then GL, then a software adapter), display lists drawn through vello_gpu with the CPU renderer's own painter (glyphs and nearest-sampled images packed into RGBA atlas pages, filtered or large images in their own textures), compositor tiles in textures, a persistent pipeline cache where the driver has one (one unsafe call, in `ffi`), and device-loss recovery that rebuilds the device and re-rasters from the retained layer tree with no app code. Golden images match the CPU renderer (RTX 3080 on Vulkan: no pixel differs visibly at 1x or 2x). `remedy-ui-host` is built: the platform-neutral host model (windows, frames, input, input-method sessions, clipboard, timers, wake, settings, memory pressure, CPU presents with damage, native handles for GPU surfaces) that every bridge implements, with `Unsupported` for what a platform cannot do. `CompositorThread` runs the compositor on its own thread: scrolling keeps the display's rate while the UI thread is stalled, and an unchanged frame presents nothing (both tested). `remedy-ui-bridge-headless` is built: the host in memory with a scripted clock, input, IME, clipboard, timers and wakes; presents copy only their damage, so tests prove damage is complete. `remedy-ui-bridge-winit` is built: one host implementation for every desktop winit serves (windows, pointer, touch, wheel and keys, IME sessions with caret area and private-input purpose, frames on redraw, timers, cross-thread wakes, softbuffer presents writing only damage when the buffer holds the previous frame, native handles for GPU surfaces); platform bridges add only `PlatformHooks`. `remedy-ui-bridge-windows` is built on it: the Win32 clipboard (sensitive copies excluded from monitors, clipboard history and cloud sync), capture protection, and real system settings; a real-window test runs the whole contract. GPU frames present to windows: `GpuSurface` picks an 8-bit RGBA/BGRA swapchain format with its own pipelines, paces to vsync, handles occluded, outdated and lost swapchains, and rebuilds itself on the new device after a device loss (tested on a real window through a resize and a forced loss). GPU validation errors are recorded rather than panicking. wgpu does not expose partial presents, so GPU windows present whole frames while the CPU path presents damage. `remedy-ui-bridge-macos` (AppKit pasteboard with concealed/transient markers for sensitive copies, `NSWindowSharingNone`, appearance, accent, contrast, motion, transparency, locale, double-click interval) and `remedy-ui-bridge-linux` (one crate for Wayland and X11: arboard clipboard with the password-manager hint, XDG portal settings over zbus, honest `Unsupported` for capture protection) are built on the shared core and lint clean when cross-compiled for macOS and Linux here; they still need a run on those machines. LCD text draws on both renderers (two passes per run: a multiply by `1 - coverage` per channel, then the color added per channel; exact over opaque pixels, grayscale inside groups), and the GPU matches the CPU. TSF is built: a safe UTF-16 text store (selection, composition, reconversion, surrounding text, edits turned into input-method events) behind a COM `ITextStoreACP` with TSF's lock protocol, one document per window, password fields with no input method; tested by driving the COM store exactly as TSF does and by TSF connecting to it on a real window. No pipeline or shader is created after start-up (wgpu resource counters, tested). Every M4 done-when item has a test. Showing old tiles scaled while new ones raster during a zoom was built with `doc-pages` in M8, its first user.

**Crates:** `paint`, `compositor`, `render-gpu`, `render-cpu`, `bridge-windows` (with TSF), `bridge-headless`.

**Contents:**
- paint chunks, layers, tiles and the commit
- compositor-side scrolling and animation
- damage-only presenting
- the start-up pipeline set, the backend ladder and device-loss recovery

**Done when:**
- golden images match between the GPU and CPU renderers
- a forced device loss recovers with no app code
- scrolling keeps the display's rate while the UI thread is artificially stalled
- an unchanged frame presents nothing
- no shader compiles after start-up in a recorded session

## M7. FreeSpeak

**Contents:**
- chat-grade lists (sticky headers, selection across rows)
- `doc-rich`, `media-anim`, `media-video`, `media-isolated`, `viz` (voice ring meters), `services-spell`
- `bridge-android`
- multi-window with moving subtrees
- the FreeSpeak skin mapping
- spaces the user builds (`widgets-board`): FreeSpeak's Home is a house that holds the voice and chat nodes plus updates, information, links and reactions, not a server list. The engine side is a board that its owner edits in place: drag, drop, resize and arrange areas and widgets (each move also doable from the keyboard, each change undoable), a registry of built-in widgets whose settings are typed so the property grid edits them, layouts saved as versioned documents that peers receive and render, reactions as a reusable component, and custom widgets people write as sandboxed scripts that build ordinary RemedyUI elements, so they are themed, accessible and fast like built-in ones. Scripts run behind one language-neutral interface, in Rhai (written by hand) or WebAssembly (compiled from Rust or any language), each an optional engine a board accepts or not: no file, network or process access, only the capabilities the board grants, with operation, time, stack and memory limits sized from the device
- the board's editor and viewer share one renderer, so what the host arranges is exactly what visitors see

**Status:** in progress. Built:
- `script`: the language-neutral interface for scripted widgets: `ScriptWidget` (name, typed settings, `render` to a description, `act` for a pressed button), `ScriptEngine` and the `Engines` registry an app or board enables, packages that name their language, the element-description protocol (columns, rows, text, buttons, links, progress, dividers as JSON; scripts describe elements and never touch them), `Limits` sized from the device (operations, time, call depth, stack, memory, element nesting) and typed errors that say which limit stopped a script (`OutOfFuel`, `TooSlow`, `TooDeep`, `TooBig`, `Denied`, `Unsupported`).
- `script-rhai`: Rhai widgets people write by hand, each in an engine of its own with only Rhai's pure standard library and the `ui` functions (no files, network, processes, `import` or `eval`; no clock or randomness, so calls are deterministic). An operation budget stops runaway loops, the time budget is checked while the script runs, the native stack it uses is measured at every step (Rhai recurses on the caller's stack), and what a call holds (its variables and the widget's state) is measured every 64 steps with every value bounded, so memory stays within twice the limit. Example widgets: `claps.rhai`, `poll.rhai`.
- `script-wasm`: WebAssembly widgets compiled from Rust or any language, run by wasmi (pure Rust, validated modules, deterministic floats) through a small ABI (`remedy_alloc`, `remedy_describe`, `remedy_render`, `remedy_act`; imports only `remedy::log` and `remedy::fail`: no WASI, a module importing anything else does not load). Fuel is handed out in slices with the clock checked between them; call depth, the interpreter's stack and linear memory are limited; a widget stopped mid-call starts over from a fresh instance. The example widget is a Rust crate (`examples/claps`) built to a checked-in module that a test rebuilds and compares.
- Both engines run in browser pages too, tested in Firefox and Chrome.
- Step budgets fit the device: each engine measures how many of its steps a millisecond buys (`StepRate`) the first time it is used, with a fixed small script or module run for a few milliseconds away from the UI thread (`exec::spawn`: a thread natively, a cooperative slice in a page), and every call long enough to time well refines it, so the rate follows thermal throttling or a power-saving mode. A low documented fallback applies only until the first measurement.
- On a board each scripted widget is an error boundary of its own (`catch_errors`): a script that stops, while loading, rendering or in a handler, is reported to `Ui::failures` and the error hook, and the widget shows why with a button that starts it again, while the board carries on.
- `widgets-board`: versioned board documents (areas on a column grid, widgets in areas; every change checked, overlaps refused), a registry of widget kinds (text, links, reactions, the app's own, scripted), one renderer for viewing and editing (selection, drag and drop, every move from the keyboard, undo and redo, settings in the property grid), and reactions as a component. Grid items now take explicit lines and spans.
- `doc-rich`: Markdown shown as themed, selectable, accessible text (headings, lists, tasks, quotes, tables, code; raw HTML stays text; links reach only the app); a rich text editor (toolbar showing what is on at the caret, Ctrl+K links, @-mention suggestions, Enter-to-send for composers) saving to Markdown that keeps every mark and block; a find bar that marks, counts and steps through matches in any part of a window.
- Rich editing in the engine: `FieldKind::Rich` edits marks (bold, italic, strike, code, links, mentions as units) and one block per line (headings, nested lists, tasks, quotes, code) on the same editing core as plain fields, with one undo history; formatted text goes to and from the clipboard as HTML on Windows, Linux and macOS, other apps' HTML coming in as allowed formatting only.
- Links inside text are real links (`El::on_link`): reachable by Tab, followed from any line they wrap onto, read as links; underlines and strikethroughs are drawn.
- Chat lists: following the latest, unread counts and a jump back, older messages loaded above without moving the view, day headers; text selection across messages; content that pops out to a window of its own and back (`movable`).
- `viz`: the speaking ring (with a muted state), level meters with peak hold and a draggable threshold, sparklines and bars, idle when nothing moves.
- `services-spell`: the platform's checker (Windows `ISpellChecker`, macOS `NSSpellChecker`) or Hunspell dictionaries, several languages at once, a personal dictionary whose changes reach every field, and the spelling menu.
- `media-anim`: GIF, APNG and animated WebP, decoded off the UI thread, shared between views, playing only while seen, with a play control under reduced motion; frames are budgeted from the machine's memory and trimmed when memory is short.
- `media-isolated`: the image loader decodes in sandboxed helper processes when the app calls `enable()` (the helper is the app's own executable, entered through `helper_main()` at the top of `main`); bytes go in and pixels come back over shared memory. Windows: a less privileged AppContainer with no capabilities (Windows Sockets cannot start in it), entered with a restricted token, created inside a job object (no child processes, no UI, a memory limit per image). Tested with hostile decoders on Windows and Linux, and each Linux layer on its own. Porting guides (`remedy_ui::guide::porting`) cover moving from egui, React, Qt or PyQt, and pywebview or HTML apps, with their code beside ours. Eight recipes in `crates/remedy-ui/examples` (chat feed, file explorer, document viewer, settings page, tray app, sticky-note windows, audio meter, unlock screen) each have a headless test in `crates/remedy-ui/tests/recipes.rs` that checks them through the accessibility tree, and a walk-through in `remedy_ui::guide::recipes`. The facade's tests, examples and doctests build with every pack (`full`, through a dev-dependency on itself; a smaller set on Android and the web, which are linted there), so `cargo test --workspace` checks all of them.

**Built so far:**
- `remedy-tools` (L7): the developer tools' logic, each group a feature (`docs`, `markup`, `scaffold`, `preview`, `testing`, `live`, `devtools`; `full` by default), typed inputs and outputs, no protocol or terminal code. The docs index (the guides, design docs, every engine crate's rustdoc and the widget catalog) is written by `cargo xtask docs-index`, committed and embedded, so a build from crates.io has the docs, and `cargo xtask check` fails when it is stale; a live checkout can be read at run time instead. Searches rank with BM25; the widget catalog lists every facade builder with its signature, feature, the element names the style sheet keys its rules by, its variants and an example. Previews build a small harness crate against the app's own `remedy-ui` (with devtools) in the app's target folder and render with the devtools' `Preview` (the CPU renderer, as golden images), returning the PNG, the screen reader's view and the audit. An app's `#[preview]` functions are listed for rendering by path. Live apps are operated over the agents listener's token-gated loopback protocol, with "asking the person" outcomes waited for and reported; remote devtools likewise. Paths stay inside the workspace the person names.
- `remedy-templates` (L7): the app templates (basic, tray, multi-window, document, android), moved out of `cargo-remedy` so `cargo remedy new` and the tools' `new_app` make the same app without either running the other.
- `remedy-mcp` (L7): the Model Context Protocol server over the official Rust SDK (`rmcp`), stdio or streamable HTTP on loopback behind a bearer token; each group a `ToolGroup`, composed by `Server::builder()` at compile time (features) and run time (`--tools docs,live`); the guides as resources, prompts for building a screen and operating an app. See [MCP.md](MCP.md).
- `cargo remedy` gained every tool as a command (`docs`, `widgets`, `rui`, `preview`, `audit`, `test`, `budgets`, `app`, `devtools`), readable by default and `--json` for scripts. See [CLI.md](CLI.md).
- Tested end to end: a scripted MCP client drives the server as a child process (docs, markup, a real preview's pixels, tests, new apps, a window operated under read-only, acting and confirming grants with a wrong token refused, its devtools), the HTTP transport's token, run-time tool selection and a docs-only build; the commands run as subprocesses against the same fixture app and window.

**Status:** in progress. Built before the freeze, the parts of the design the code lacked:
- **Context:** `provide_context`/`use_context` over the reactive owner chain (`Owner`, scope context), and `El::provide`, `El::use_context`, `El::child_with` over the element tree. Windows' content is built with the app and its persisted-state store provided.
- **Control flow:** `show(ui, cond, build)` with a fallback and enter and exit transitions (leaving content stays inert until its exit ends); `catch_errors(ui, fallback, child)` containing panics in building, handlers, bindings, effects and painters, with the element path, source location and phase, a retry, the window's failure list and an error hook (effects reach boundaries through a reactive `ErrorSink` and the runtime's panic handlers; the tree hands its failures to the view); `suspense(ui, placeholder, child)` with a delay before the placeholder and a minimum time shown.
- **Resources:** `Resource` fetches off the UI thread on an `Executor` (the shared `WorkerPool` unless one is provided as context), cancels on key change and disposal, and registers with the nearest `Suspense` when read. No async runtime.
- **Persisted signals:** `Signal::persist("key")` (reactive feature `persist`, on in the facade) in a `PersistStore`: debounced, atomic JSON writes off the UI thread, versions and migrations, files of newer versions left alone; `App::persist_store` is `<data>/state`, flushed on quit.
- **Properties:** `IntoProp` (a value, signal, memo or closure) for `text`, `disabled`, `variant`, `semantics`, `style` and the core widgets' labels; `style_dyn`, `disabled_dyn` and `semantics_dyn` are gone, `text_dyn` stays deprecated because FreeSpeak uses it.
- **Typed tokens:** `Space`, `Radius`, `TextRole`, `ColorRole`, `Dp`, `Pad` and token `Style` patches, taken by `gap`, `width`, `height`, `padding` and `style`, resolved through the theme and again on each theme change.
- **Previews:** `#[preview(...)]` (themes, locales, sizes, text scales) makes a `PreviewSpec` and a golden-image test; `#[previews]` lists a module's previews for the gallery.
- **Motion:** `El::animate`/`animate_then`/`animate_style` on the frame clock (springs and tweens from `remedy-ui-motion`, interruption from the current value and velocity, instant under reduced motion), `remedy_ui::motion`, and `PaintCx::time` and `reduced_motion` so painters animate without timers (the spinner and indeterminate progress now do).
- **Lists:** `for_each`, `list` and `virtual_list` take a `SignalVec` and apply its operations (one row per push or insert, nothing built for moves and removals, rows built in scopes of their own); list rows give screen readers a merged name, place in set and selection; tree rows select on an assistive Click and open and close through Expand and Collapse (`El::on_accessibility_action`).
- **Keyed transitions, failures page, element ownership:** `for_each_with` plays enter and exit transitions and glides staying rows to new places (`El::flip`, FLIP), instant under reduced motion; the inspector's Failures page lists caught failures (message, phase, element path, source location) with Retry for boundaries still failed and Clear (`Ui::clear_failures`, `retry_failure`, `is_failed`); elements' scopes are owned by nothing (`Scope::detached`, reading context where they were built) and their bindings by their scope (`Effect::new_in`), so content built while a binding runs keeps its bindings when that binding runs again. An audit of the widget packs found their bindings either clear and rebuild what they build, or already build in scopes of their own (board reactions, lists, `show`, boundaries); the fix covers app code that keeps content built in a binding, such as a page pushed onto a `NavStack` from a route binding.
- **Smaller fixes:** every OSC 52 request in one sync reaches the app in order; terminal text exports leave out trailing blank rows; `thumbnails` has its own width and `page_view` never takes its height from its pages; pseudo-locales reach screen readers and the inspector.
